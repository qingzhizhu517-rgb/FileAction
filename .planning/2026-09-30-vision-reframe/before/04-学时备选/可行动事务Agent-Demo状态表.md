## 赛事要求与建议时间分配

**官方要求：5 分钟展示 + 3 分钟问答，至少 3 名评委。** 下列拆分只适用于学时备选，是团队建议，不是新推荐主线或赛事指定脚本；三条件、七屏和 180 秒核心操作也不是赛事硬指标。

| 正式展示时间 | 团队建议内容 |
|---|---|
| 0–40s | 谁遇到什么问题，为什么需要逐条核对，当前样例的数据性质 |
| 40–220s | 本文现有 180 秒核心操作：输入、审核、缺口、证据、what-if 与清单 |
| 220–270s | 技术分工、可复用底座与本届实际新增贡献；只讲已经完成的内容 |
| 270–300s | 场景价值、尚未支持的范围与下一步验证 |
| 展示结束后的 3 分钟 | 回答实现、数据来源、复用/新增及限制等追问 |

**以下状态中的 0–180 秒均是核心操作的相对时间，换算为台上时间需加 40 秒。** 核心演示不是完整 5 分钟展示，也不是算法延迟承诺。

10 月 1 日晚须提交的 **60 秒团队视频**与最终演示录屏是两个交付：首晚视频介绍团队、问题和计划即可，不要求此时已有最终作品。10 月 4 日 09:30 封包，备用录屏必须此前提交。作品须能运行，核心流程须实际完成；透明的录像或输入说明不能替代未完成的软件。

## 一、演示要证明的链路

```text
制度与个人记录 → 已审核要求 → 已认定事实 → 有依据的比较 → 缺口 → 可确认清单
```

本备选要呈现的转折：总量足够，不代表已核验的分类要求都满足。仅在本备选中核验总量、创新创业、文艺体育三个条件，其他分类显示「已导入，未核验」；全程保留覆盖范围。

下文的学时、阈值等业务样例数值均为**合成验收样例，非真实学校规则或个人成绩**。对应样本文件尚待制作；不能把文档截图当作应用实测。

| 阶段 | 时间 | 拟证明的能力 |
|---|---|---|
| 理解与审核 | 0–62s | 来源可读取，规则候选能回到原文并由人审核 |
| 比较 | 62–82s | 已审核要求与同口径个人事实逐条比较 |
| 核查 | 82–125s | 已知缺口可计算，规则和事实双方有来源 |
| 行动 | 125–180s | 假设试算、制度途径与清单导出不混淆真实认定 |

## 二、真实性规则

界面必须同时显示数据性质和输入方式，不用「输入可预置」掩盖抽取环节：

| 方式 | 展示要求 |
|---|---|
| 真实数据、现场抽取 | 使用有授权的实际文件，展示真实任务状态和必要审核；失败不能自动切换成功结果 |
| 真实数据、人工核验输入 | 可以用已审核快照继续真算，明示人工环节；不能称现场完成自动抽取 |
| 合成验收样例 | 输入文件和界面均标合成；真实运行计算可以证明逻辑，但不能证明真实学校可用 |
| 公开制度 + 合成个人记录 | 逐份标识制度来源与合成记录，说明未完成真实教务接入；不可把整组材料称为真实个人数据 |
| 缓存回放 | 标示回放及原运行时间，保留输入、版本和日志；不能称本次现场运行 |

演示结果不得硬编码；证据必须指向存在的来源；日志仅对应实际发生的操作。不改真实成绩来制造缺口，不为了同时展示四态拼出互相矛盾的主样例。

180 秒是核心操作讲解预算，不是解析与审核的性能承诺。预审输入、合成记录和回放须披露，这属于团队的真实性要求，不代表赛事已特批该方式；不能用它们冒充未完成的核心流程。备用录屏必须在封包前提交，并在播放时明确标示。

赛前可以准备通用环境、了解公开资料、组队并讨论创意和方案草图。正式开发安排在 10 月 1 日 14:30—10 月 4 日 09:30；已有底座的复用与本届新增分开说明，不把赛前已完成的核心功能、成品或完整主题视频冒充现场成果。

## 三、七屏与十一个状态

### 屏 A：问题屏

#### 状态 0 · 提出问题（0–8s）

| 项 | 内容 |
|---|---|
| 屏幕 | 简洁标题、所选文件组、数据/输入模式标记 |
| 文案 | 「总量够了，分类也够了吗？」 |
| 数据 | 合成样例预览可出现「总量 128 / 120」，须标「样例预览」；本次结果尚未计算 |
| 目的 | 让观众先理解一个明确的核对问题 |
| 注意 | 不承诺全校认定结果，不把预览伪装为现场解析结果 |

### 屏 B：输入屏

#### 状态 1 · 读取来源（8–20s）

| 项 | 内容 |
|---|---|
| 屏幕 | 拖拽区与文件选择按钮，逐文件角色、格式及真实任务状态 |
| 输入 | 团队拟用 1–2 份文本 PDF 制度 + 1 份所选格式 CSV 记录；可用合成个人记录并明确标示，不强行凑三份文件 |
| 操作 | 选择或拖入文件，校验后进入解析；未知格式、扫描件、损坏文件可见报错 |
| 目的 | 证明系统读取了选定样本，保留可追溯的来源 |
| 注意 | 动画不得假造进度；不承诺「导出什么都能直接用」 |

### 屏 C：规则与来源屏（20–62s）

#### 状态 2 · 抽取并核对（20–42s）

| 项 | 内容 |
|---|---|
| 屏幕 | 左侧原文或 CSV，右侧候选条件；总量与分类分组 |
| 数据 | 总量 ≥120、创新 ≥20、文体 ≥10；规则来源和个人记录分开 |
| 操作 | 点击创新要求，定位原文；点击事实，显示 CSV 行列 |
| 目的 | 展示候选结构如何对应来源 |
| 注意 | 未定位的引用标记失败，不整页高亮冒充精确引用 |

#### 状态 3 · 确认适用范围（42–62s）

| 项 | 内容 |
|---|---|
| 屏幕 | 学校、制度版本、适用群体、统计时点、审核记录和覆盖范围 |
| 数据 | 「本次核验 3 个条件；其他必需条款尚未完成核验」 |
| 操作 | 在可行时间内审核关键候选，或明确显示所用的已审核快照 |
| 目的 | 说明系统只在确认的规则与数据范围内计算 |
| 注意 | 审核不能用定时动画模拟；未审核候选不得悄悄用于确定判定 |

### 屏 D：条件比较屏

#### 状态 4 · 同口径比较（62–82s）

| 项 | 内容 |
|---|---|
| 屏幕 | 要求、已认定事实、结果三列；文字状态与颜色同时出现 |
| 数据 | 总量 128 ≥120；创新 12 <20；文体 0 <10 |
| 结果 | `SATISFIED`、`CONFLICT`、`CONFLICT` |
| 目的 | 显示真实计算，而非仅把关键词连线 |
| 注意 | 明确 0 是未达标，缺记录才是 `MISSING`；规则或证据不确定为 `UNKNOWN` |

### 屏 E：缺口与证据屏

#### 状态 5 · 展示已知缺口（82–105s）

| 项 | 内容 |
|---|---|
| 屏幕 | 上方总量 128/120；下方创新差 8、文体差 10；其他四类标未核验 |
| 汇总 | 「已核验的两类存在 18 学时已知缺口；制度覆盖不完整」 |
| 目的 | 呈现总量达标与分类不足同时成立 |
| 注意 | 不写「补 18 学时即可通过」；总量进度不是资格进度，不能让总进度条表示整体完成 |

#### 状态 6 · 展开双方证据（105–125s）

| 项 | 内容 |
|---|---|
| 屏幕 | 点击创新差值，侧栏显示规则原文、记录行列、审核状态和计算式 |
| 示例 | 规则要求 20，记录已认定 12，因此 `max(0,20−12)=8` |
| 目的 | 观众能够检查系统为什么得到该差值 |
| 注意 | 四态均可打开详情；缺失或未知显示待补内容/原因，不能填入虚构来源 |

### 屏 F：假设与行动屏

#### 状态 7 · what-if 试算（125–145s）

| 项 | 内容 |
|---|---|
| 操作 | 在独立假设区加入「创新 +10 学时且获得认定」 |
| 屏幕 | 基线与假设并列；假设总量 138、创新 22、文体仍 0 |
| 结果 | 「假设创新缺口清零；文体仍差 10；其他规则未核验」 |
| 目的 | 证明系统会重新计算受影响的条件 |
| 注意 | 假设前提包括单位、计入资格和时限；不把拟参加活动记为真实已认定，重复假设事件不重复计入 |

#### 状态 8 · 形成补充清单（145–162s）

| 项 | 内容 |
|---|---|
| 屏幕 | 按类别列已知缺口、制度允许途径、对应条款、待核实资格与截止期 |
| 操作 | 用户确认希望加入清单的事项 |
| 目的 | 把计算转为可执行的下一步核实与准备 |
| 注意 | 制度途径不等于当前可报名活动。无活动数据就标「可报名性待核实」；无途径证据时建议向学院确认，不编活动或耗时 |

### 屏 G：确认与回环屏

#### 状态 9 · 确认并导出（162–174s）

| 项 | 内容 |
|---|---|
| 屏幕 | 清单摘要、范围与未知项、确认导出按钮 |
| 操作 | 选择事项后生成实际可下载的 Markdown 清单 |
| 目的 | 形成可检查的产出，保留用户选择 |
| 注意 | 导出失败必须提示；不能只记录一个确认值就宣称已导出。不自动提交学校系统 |

#### 状态 10 · 回到原问题（174–180s）

| 项 | 内容 |
|---|---|
| 屏幕 | 原文件组旁出现本次核验结果与清单下载入口 |
| 汇总 | 「核验 3 个条件；发现 2 类已知缺口；依据可查看；下一步已列清单」 |
| 目的 | 让观众复述文件如何转成个人可检查、可行动的信息 |
| 注意 | 保留合成/真实、人工核验/回放和部分覆盖标签，不在结尾升级为整体认定结论 |

建议结束语：**「它把选定制度里的要求，与有来源的个人记录逐项核对，说明已知缺口和下一步需要确认什么。」**

## 四、状态与屏幕映射

| 屏 | 状态 | 核心演示内时间 | 核心内容 |
|---|---|---|---|
| A | 0 | 0–8s | 问题与样例标识 |
| B | 1 | 8–20s | 文件输入 |
| C | 2、3 | 20–62s | 来源、候选与审核 |
| D | 4 | 62–82s | 三个条件的比较 |
| E | 5、6 | 82–125s | 缺口与双方证据 |
| F | 7、8 | 125–162s | 假设与补充清单 |
| G | 9、10 | 162–180s | 确认导出与回环 |

七屏承载十一个状态，切换不超过六次；可以合并为三个工作面。无法在 180 秒内讲清时，先减动效与重复说明，不删掉审核、证据、未知项或范围标记。

## 五、赛中关键检查与交付准备

以下是选用学时备选时的检查清单，数量不是新增赛事门槛；新推荐主线的范围与检查应根据 Idea 完善方案另行确定。

- [ ] 选定制度、版本、适用群体与一种 CSV 格式；公开制度、真实个人记录和合成个人记录逐份标识，真实个人数据有权使用并脱敏。
- [ ] 建立能打开的样本文件、引用和人工标准答案；验证合成分类合计 `32+18+24+12+0+42=128`。
- [ ] 检查主流程、阈值前/等于/超过、有效 0、缺证、`UNKNOWN`、部分覆盖与来源定位；记录实际结果和失败。
- [ ] 验证假设创新 +10 后总量 138、创新 22、文体仍差 10，退出假设后基线不变。
- [ ] 检查实际导出的文件与当前快照、范围、证据及未知项一致。
- [ ] 按可用时间演练完整 5 分钟展示和 3 分钟问答，记录实际耗时及是否使用预审输入/录像。
- [ ] 10 月 1 日晚提交 60 秒团队视频；10 月 4 日 09:30 前完成作品封包和备用录屏提交。建议作品包包含运行入口、必要源文件、运行说明、录屏、复用/新增及素材权限说明，不推定必须公开开源。

30 条规则边界用例、10 组端到端样例、两组独立真实样本和至少三次彩排，留作赛后扩展验证建议，详见 UI 规格。它们不作为当前 idea、报名或本届现场交付的数量门槛。

四态备用案例单独运行：删除合成记录中的某类事实，期望 `MISSING`；改为仅有待认定证书或不明确换算，期望 `UNKNOWN`。这些是合成边界测试，不修改真实记录，不与主样例同时混显示。

## 六、常见追问的可核实回答

| 问题 | 建议回答 |
|---|---|
| 「这是不是 RAG？」 | 检索可以帮助找到条款；本 Demo 要额外证明已审核规则、固定输入、确定比较和双方证据。其他系统也可能实现这些能力，差异要靠同题实测。 |
| 「换个学校能用吗？」 | 当前只计划支持一校一版及所选 CSV 格式；换校要重做规则适配、人工审核和验收。 |
| 「有引用就一定正确吗？」 | 不一定。引用可能不适用或被误读，所以保留规则审核、版本范围、未知状态和真实边界测试。 |
| 「为什么只核验三项？」 | 先验证一条完整链路。其他规则明确标未核验，因此不输出学校整体认定结论。 |
| 「加 10 学时就完成了吗？」 | 只是创新类的条件试算；文体仍差 10，活动也须实际完成并获得认定。 |
| 「现场时间够吗？」 | 正式窗口是 10 月 1 日 14:30 到 10 月 4 日 09:30，共 67 小时，包含休息与赛事活动。按实际成员收敛核心流程，界面可合并；不把总窗口当净开发工时。 |
| 「首晚就要交成品视频吗？」 | 首晚是 60 秒团队视频，说明问题和计划；最终作品与备用录屏须在 10 月 4 日 09:30 封包前提交。 |

竞品比较应使用同一批获授权样本、相同问题和标准答案，记录数值、缺失/例外处理、引用定位及修改后重算表现；没有实测前不宣称竞品不能计算或不能判定。
