# 学分认定 Demo · 场景规格

> **校园主 Demo 从「奖学金申请」换成「第二课堂学分认定」。**  
> 通用架构（Condition / UserFact / MatchResult / Gap / 证据链）完全复用，只换受控词表与 Demo 数据。  
> 配套：[[可行动事务Agent-UI原型规格表]] · [[可行动事务Agent-内部筛选速览]]



---

## 一、为什么这个场景更好（四条例由）

### 理由 1 · 它命中的是「总量达标 ≠ 分类达标」——学生最痛、最看不见的地方

学分认定的真实结构是**双约束**：

| 约束       | 内容                                                           |
| -------- | ------------------------------------------------------------ |
| 总量约束     | 第二课堂总学时 ≥ 120                                                |
| **分类约束** | 社会实践 ≥20、创新创业 ≥20、文艺体育 ≥10、志愿服务 ≥10、思想成长 ≥20 …（**各类不可互相抵扣**） |

于是出现最典型、也最让人崩溃的情况：

> **总学时 128 / 120，看起来早就够了；但「创新创业」只有 12 学时，某一类不满就通不过认定。**

学生自己在教务系统里看到的是一个总数——**看不出是哪一类不够**。这正是系统能做、而人做不到的那件事。

### 理由 2 · 输出的是「数量缺口」，不是「资格判定」——后者更可行动

|          | 奖学金场景          | 学分认定场景           |
| -------- | -------------- | ---------------- |
| 核心动作     | 判定你是否符合条件      | 算你还差多少           |
| 输出       | 资格判定（合格 / 不合格） | **数量缺口（差 8 学时）** |
| 用户感受     | "我不行"          | "再修 8 个学时就行"     |
| 能否直接生成任务 | 勉强             | **天然可以**         |

> **数量缺口比资格判定更可行动**——它能直接变成一条待办，而不是一个结论。这让「Gap → Action」这一跳变得毫无阻力。

### 理由 3 · 判定是纯数值，规则引擎完美适配

学分 / 学时是数字，阈值比较是纯代码。**完全符合「LLM 只归一化、规则做判定」的架构**，不需要 LLM 做任何判断。

→ Demo 的判定层可复现、可解释、零幻觉风险。

### 理由 4 · 无学术诚信风险

不像「生成申请材料」那样踩红线——这里系统做的是**算数与列清单**，没有任何代写成分。

**顺带的好处**：`readiness` 在这个场景里是一条**真正的进度条**（已修学时 / 要求学时），比奖学金场景里抽象的"已满足条件数 / 总条件数"直观得多。

## 二、输入：三份文件拼出一个答案

| # | 文件                 | 提供什么                | 来源         |
| - | ------------------ | ------------------- | ---------- |
| 1 | **人才培养方案**         | 总学分构成、二课各分类的学时要求    | 学院发布       |
| 2 | **第二课堂（育人）学分认定办法** | 各类认定标准、可认定途径、每项折算学时 | 学生处 / 团委   |
| 3 | **个人已修学分与二课记录**    | 我的实际学时、已认定明细        | **教务系统导出** |

### ⚠️ 关键卡点：第三份数据从哪来

这是本场景**唯一的工程风险**，必须赛前确定：

| 方案                            | 可行性       | 说明                                                        |
| ----------------------------- | --------- | --------------------------------------------------------- |
| **A. 教务系统导出 PDF / Excel，再上传** | ✅ **推荐**  | 教务系统普遍支持导出学分统计与二课记录。**而且这恰好正面证明"无痛输入"**——用户不需要整理，导出什么就丢什么 |
| B. 截图 + OCR                   | 🟡 备用     | 展示"拍一张就进来"的效果，但 OCR 误差会削弱可信度                              |
| C. 教务系统对接                     | ❌ 72h 不可行 | 需要学校授权与接口，不做                                              |

> **推荐 A**，并在路演话术里点明：**"我不需要你整理，你从教务系统导出什么，就直接丢进来。"**

### 多文件关联本身就是亮点

单文件摘要做不到这件事——**答案藏在三份文件的交叉处**。这正面回应了"为什么需要关联能力，而不是 PDF + 聊天"。

## 三、受控词表（本场景）

### 顶层

| key                        | label | kind      | 说明        |
| -------------------------- | ----- | --------- | --------- |
| `total_credit`             | 总学分   | threshold | 培养方案总学分要求 |
| `second_class_hours_total` | 二课总学时 | threshold | **总量约束**  |

### 二课分类（**分类约束，各类不可抵扣**）

| key                  | label | kind      | 典型要求    |
| -------------------- | ----- | --------- | ------- |
| `sc_social_practice` | 社会实践  | threshold | ≥ 20 学时 |
| `sc_innovation`      | 创新创业  | threshold | ≥ 20 学时 |
| `sc_arts_sports`     | 文艺体育  | threshold | ≥ 10 学时 |
| `sc_volunteer`       | 志愿服务  | threshold | ≥ 10 学时 |
| `sc_thought`         | 思想成长  | threshold | ≥ 20 学时 |
| `sc_skill`           | 技能特长  | threshold | ≥ 10 学时 |

> ⚠️ 72h 只需真实覆盖 **1–2 类**（建议 `sc_innovation` + `sc_arts_sports`），其余按汇总数字展示。**不要试图覆盖全部类别**——规则一多，抽取出错概率陡增。

## 四、数据模型实例

### Condition（从《认定办法》抽取）

```jsonc
{
  "id": "cond_sc_innovation",
  "key": "sc_innovation",
  "label": "创新创业学时",
  "kind": "threshold",
  "operator": ">=",
  "value": 20,
  "unit": " 学时",
  "scope": "category",            // total | category —— 区分总量约束与分类约束
  "required": true,
  "raw_quote": "创新创业类不少于20学时",
  "source_span": { "page": 1, "quote": "创新创业类不少于20学时" },
  "source_doc": "第二课堂学分认定办法.pdf",
  "confidence": 0.96
}
```

> 新增字段 **`scope`**：本场景必须区分「总量约束」与「分类约束」，否则算不出"总量够了但某一类不够"这个核心结论。

### UserFact（从教务导出文件抽取）

```jsonc
{
  "id": "fact_sc_innovation",
  "key": "sc_innovation",
  "label": "已修创新创业学时",
  "value": 12,
  "type": "number",
  "evidence_id": "ev_011"
}

// Evidence
{
  "id": "ev_011",
  "fact_id": "fact_sc_innovation",
  "source_file": "第二课堂学时统计_2026导出.pdf",
  "source_loc": "第 2 页 · 创新创业类",
  "snippet": "创新创业  已认定学时：12",
  "verified": true
}
```

## 五、四态在本场景的映射（比奖学金场景更自然）

| 状态          | 判定规则       | 本场景表现               |
| ----------- | ---------- | ------------------- |
| `SATISFIED` | 已修 ≥ 要求    | ✓ 志愿服务 18 / 10      |
| `CONFLICT`  | **有学时但不够** | ⛔ 创新创业 12 / 20      |
| `MISSING`   | **完全未修**   | ⚠ 文艺体育 0 / 10       |
| `UNKNOWN`   | 无法自动判定     | ? 技能特长：证书已提交，认定结果未出 |

> **`CONFLICT` 与 `MISSING` 在这个场景里天然分开**——"修了但不够"和"完全没碰"是两种完全不同的行动优先级。奖学金场景里这两种要靠设计硬造，这里它们本来就存在。

## 六、Demo 输出示例（这就是要投到屏幕上的东西）

```
【第二课堂（育人）学分认定】

总量  128 / 120 学时   ✓ 已达标
      ← 注意：总量已够，但下面有 2 类不达标

分类明细
  ✓ 社会实践      32 / 20
  ✓ 志愿服务      18 / 10
  ✓ 思想成长      24 / 20
  ⛔ 创新创业      12 / 20    差 8 学时
  ⚠  文艺体育       0 / 10    差 10 学时
  ?  技能特长     待认定       证书已提交，结果未出

结论：你还差 2 类共 18 学时，才能通过认定。
      总量达标 ≠ 认定通过。

下一步（依据《认定办法》第 4 条反查可补途径）：
  · 创新创业类：校级大创项目结项（计 10 学时）/ 学科竞赛获奖（计 6–12 学时）
  · 文艺体育类：校级文艺演出、社团展演（每项 2–4 学时）
  → 生成待办清单？
```

### 一个关键设计：修复路径不需要额外数据源

「**具体修哪个、怎么补**」的答案**就在《认定办法》文本里**——它本身会写明哪些途径可认定、每项折算多少学时。

所以 `Gap → Action` 这一跳只用到已输入的三份文件，**不需要再引入活动列表、报名系统等新数据源**。这既是架构上的省事，也是论证上的漂亮：**系统把同一份制度文件用在了两次——一次用来判定要求，一次用来反查修复路径。**

## 七、相对奖学金 Demo，哪些屏需要改

| 屏       | 变动                                                |
| ------- | ------------------------------------------------- |
| A 问题屏   | 文案换成本场景痛点（"总学时明明够了，为什么认定就是过不了？"）                  |
| B 输入屏   | **改成拖入 3 份文件**（培养方案 / 认定办法 / 个人学时统计）——这里正好体现多文件关联 |
| C 规则解析  | 条件卡按 **总量 / 分类** 分组展示，`scope` 字段可视化               |
| D 条件匹配  | 左列「认定要求」× 右列「我的已修学时」，连线显示差值                       |
| E 缺口屏   | **本屏是全场高潮**：总量达标 + 分类不达标同屏对比；`readiness` 变成真正的进度条 |
| F 执行屏   | 从"整理材料包"改成「**生成补修清单**」——依据认定办法反查可补途径              |
| G 确认与回环 | 汇总变为"还差 2 类 18 学时 + 已生成补修清单"                      |

**屏 A / E / F 三屏的改造成本最低、收益最高**，优先做。

## 八、72h 范围与风险

### 必须真做（🟢）

- 从 3 份真实文件中抽取出：总量要求、分类要求、个人实际学时
- **总量 vs 分类双约束的判定**（这是本场景的技术核心）
- 差值计算与排序（"先补哪个"按缺口大小 + 可获取难度）
- 依据条款反查可补途径

### 可以预置（🟡）

- 个人学时数据（= 用户已从教务导出，合理）
- 培养方案与认定办法全文（真实文件，只是抽取范围可限定）

### 风险清单

| 风险             | 说明                             | 应对                            |
| -------------- | ------------------------------ | ----------------------------- |
| **教务数据获取方式未定** | **本场景第一风险**。赛前必须确认能导出真实学时统计    | 提前找 1 位同学实测导出流程；导不出就降级为截图 OCR |
| 分类规则过多         | 二课类别多，全量抽取易错                   | **只真做 1–2 类**，其余按汇总数字         |
| 认定规则有例外条款      | 《认定办法》常有"特殊情况由学院认定"            | 这类条款 → `UNKNOWN` 态，正好展示诚实边界   |
| 学时数字对不上        | 教务导出与认定办法口径可能不一致（学时 / 学分 / 次数） | **赛前先人工核对一遍**，单位换算规则写死在词表里    |

> ⚠️ 最后一条最容易被忽略：**认定办法常混用"学时"与"学分"**（如 1 学分 = 16 学时）。若不统一单位，算出的缺口会全错——而且错得很自然，不容易发现。**必须先定义单位换算，再动代码。**

## 九、与奖学金场景的关系

**奖学金不废弃，降为「机会类」的佐证。**

| 用途         | 场景                                    |
| ---------- | ------------------------------------- |
| 校园主 Demo   | **学分认定**（Obligation：别人要求你做，且你有明确的量要补） |
| 一句话佐证 / 备用 | 奖学金申请（Opportunity：同一套能力同样适用于机会类文件）    |

路演时一句话带过即可：**"同一套能力，换成奖学金通知，输出的就是资格判定与材料缺口。"** —— 这一步把"一个场景的工具"升级成"一类能力"。
